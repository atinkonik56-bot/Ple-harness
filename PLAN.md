## 1. What the competition actually wants

An **open-source autonomous agent harness** (a server, not a prompt) that solves real engineering work. 85 expert-reviewed tasks total: **29 public dev tasks** (for development + committed `artifacts/`) and **56 hidden test tasks** (6 Structural, 9 Civil, 18 Electrical, 23 Mechanical).

Each task runs up to **6 hours** in an isolated container and asks for a project deliverable: a calculation package, design review, drawing, or technical memo. Grading per task (0.0–1.0) = automated verifier scripts (quantitative calculations, CAD/IFC geometries, constraints) + an LLM judge (Claude Opus 5.5) for open-ended deliverables.

### Two stages

**Stage 1 — Writeup gate (100 points).** A Kaggle Writeup (≤ 2,000 words) scored on 5 criteria; **top 100 advance**:

| Criterion | Pts | What judges want |
|---|---|---|
| 1. Insight & Failure Analysis | 25 | Non-obvious lessons about engineering agents; real dev-set failures (misread drawing callout, wrong code clause, unit errors, stopping early); controlled ablations ("we added X, dev score went A→B"); ideas that failed |
| 2. Engineering Reasoning | 25 | Walk through one concrete dev task; compare agent trajectory vs a licensed engineer's workflow; where reasoning held, where it shortcut, which domain skills (reading CAD/PDF drawings, checking code tables, running solvers) separated passes from failures |
| 3. Cross-Model Generalizability | 15 | Test on the 29 dev tasks with **≥ 2 models** (incl. local open-weight / personal API); report what helps every model vs one model only; accuracy-vs-cost shift. Commit ONE target `google-cloud/<id>` `model_api` in `submission.yaml` |
| 4. Efficiency & Scaling | 20 | Plot dev score vs compute budget (calls, tokens, runtime, parallel attempts); mark where accuracy plateaus; estimate remaining headroom |
| 5. Clarity & Visuals | 15 | Written for an ML researcher with NO civil/mech/electrical background; headline finding near the top; the 3 required figures; under 2,000 words |

Required figures: (1) architecture diagram, (2) score-vs-cost plot, (3) dev-set failure breakdown. Un-submitted drafts are NOT judged.

**Stage 2 — Hidden evaluation.** Top 100 run all 56 hidden tasks, **3 independent times each** (168 task runs). Ranking: **mean score among systems on the performance–cost Pareto frontier**; finalists need **mean ≥ 0.138** to qualify for the frontier. 1st/2nd/3rd by Stage 2 mean score on the frontier. Ties break on Stage 1 Writeup score, then earlier Kaggle submission timestamp.

### Minimum requirements (all four must pass for Stage 1)

1. Kaggle Writeup covering all 5 rubric criteria + 3 figures.
2. GitHub repo link + 40-char commit SHA under Project Links. Repo root must include `submission.yaml`, `serve.py` / `harness.py`, an Apache-2.0 or MIT license, and the unpacked `artifacts/` directory. Repo may be private during the competition if the ple-submission GitHub App is installed; **must be public at competition close**.
3. `model_api` in `submission.yaml` = one of the 11 official `google-cloud/<id>` models (see §3). No GCP/Vertex billing needed for local dev; in Stage 2 the eval proxy blocks custom API keys (`.env`), external model servers, and web search — **Google supplies the eval key free**.
4. Pass `uv run python -m kit check` and `uv run python -m kit artifacts` via the PLE Competition Kit. Committed `artifacts/` must be an unpacked directory (≤ 512 MiB, ≤ 10,000 files, no Git LFS/symlinks) generated by `uv run python eval/run.py`. Switching `model_api` to the target model after generating artifacts locally does NOT disqualify; paid LLM-judge API calls are NOT required for local dev — document the local model + judge setup in the Writeup; organizers re-score `artifacts/` with the official judge.

### How an entry runs (Stage 2)

Evaluator clones the commit, runs `install` once in a `debian:bookworm` container (30-min timeout, `/opt/harness` capped at 2 GiB compressed), then a smoke test (`serve` binds `0.0.0.0:$PORT` within 120 s, writes a test file, sends `done`). It re-grades committed `artifacts/` on the 29 dev tasks and re-runs a random dev sample live — **failures of reproducibility or hard-coded outputs = disqualification**. Then per hidden task: agent runs in an isolated container (**2 CPUs, 4 GB RAM, read-only `/opt/harness`, writable 1 GB `/tmp` + `$HOME`, 6 h limit**) over WebSocket. Invalid requests (HTTP 400), unrecovered crashes, and timeouts count against the score; `ungraded` or timed-out tasks without a `done`/`error` frame score 0.0.

## 2. The task domain (what is new vs Gemma)

| Discipline | Tasks (bench) | Typical deliverables |
|---|---|---|
| Structural | 10 | Gravity/wind/seismic load checks, member + connection checks, seismic design bases, drawing revisions from review comments |
| Civil | 18 | Settlement + bearing capacity, foundation strategy, site layout, grading/drainage, construction sequencing + temporary works, cost estimates + fee positions |
| Electrical | 27 | Load + capacity calculations, plan-review responses, energization checks, cable sizing, specifications, drawing records |
| Mechanical | 30 | Cooling + controls, clash-free MEP routing, equipment equivalency, storage-tank service life, fire-test validation |

The agent's job is NOT "answer a question". It must **produce a graded engineering artifact from a messy project folder** — reading drawings (CAD/PDF), checking code tables and clauses, running calculations with correct units, and writing files (calc package, memo, revised drawing records) that a verifier can check numerically.

Failure modes the rubric explicitly names: **misreading a drawing callout, picking the wrong code clause, unit errors, stopping early**. These are the design targets — the harness wins by preventing exactly these.

## 4. Harness design (v1)

Start from the kit's compact custom starter **`sample_submissions/plan-verify`** (not from an agent adapter like `pi-opus` — we want full control of the verification loop), and extend it. First build step: clone `google-research/ple`, read `kit/README.md`, `docs/protocol.md`, `docs/models.md`, `eval/README.md`, and compare the starters (`minimal`, `plan-verify`, `custom-openai`).

### Architecture

```
Task prompt arrives over WebSocket (evaluator)
        │
        ▼
┌──────────────────────────────────────────────────────────────┐
│ serve.py — WebSocket server (binds 0.0.0.0:$PORT, ≤120 s)    │
│  · reads model URL/key from env only (MODEL_BASE_URL, ...)   │
│  · drives ONE task: plan → act → verify → deliver → done     │
│  · sends `done` on success, `error` on unrecoverable failure │
│  · hard budget guards: wall-clock, model calls, tokens       │
├──────────────────────────────────────────────────────────────┤
│ Agent loop (per task, ≤ 6 h)                                 │
│  1. SURVEY — inventory project files; read task prompt;      │
│     identify deliverable type + governing code/standard;     │
│     list the checks the deliverable must satisfy             │
│  2. PLAN — decompose into calculations/checks; name the      │
│     code clause or table each check rests on; state the      │
│     units of every quantity up front (unit ledger)           │
│  3. COMPUTE — run solvers as scripts (Python calc, never     │
│     mental arithmetic for numbers that matter); write        │
│     intermediate results to files, not to context            │
│  4. VERIFY — independent re-check, different method:         │
│     recompute key numbers with a second script; unit audit   │
│     against the ledger; check each number against the code   │
│     table/clause; CAD geometry checks where applicable;      │
│     at most 2 revise cycles, then deliver best effort        │
│  5. DELIVER — write final deliverable files; self-check      │
│     each against the task's stated requirements; send done   │
├──────────────────────────────────────────────────────────────┤
│ Tools (task-container protocol: shell / read / write / MCP)  │
│  · run_command (calculators, PDF/CAD text extraction, grep)  │
│  · read_file / write_file (deliverables + intermediates)     │
│  · task-local MCP servers: documents, spreadsheets, email,   │
│    CAD (per kit docs — confirm names in docs/protocol.md)    │
├──────────────────────────────────────────────────────────────┤
│ Skills (adapted from Gemma — see §5)                         │
│  · doc-locator: BM25 over project docs/drawings/code text    │
│  · verifier-runner: run verifier scripts, summary only       │
│  · unit-ledger: every quantity carries units; audit script   │
│  · calc-checker: recompute with an independent script        │
└──────────────────────────────────────────────────────────────┘
```

### Design bets (what should move the score)

1. **Verification loops are the product.** The competition brief says it outright ("engineer the verification loops"). Gemma taught us the same lesson in miniature: a reproduce-first loop + a test-runner summary beat a bigger model. Here the analogue is: no number enters a deliverable unless a second, independent computation confirms it.
2. **A unit ledger, enforced by script.** Unit errors are a named failure mode. Every quantity the agent states gets recorded with units; a script audits the ledger for dimensional consistency before delivery. This is cheap, deterministic, and exactly the kind of thing a pure-LLM agent gets wrong.
3. **Cite the clause, then compute.** Picking the wrong code clause is a named failure mode. The doc-locator skill retrieves the governing clause/table text; the agent must quote it in its working notes before using its numbers. (No web in Stage 2 — all domain knowledge must come from the task's own files, the prompt, or baked-in reference tables.)
4. **Context discipline from Gemma.** Never paste full tool output / full PDFs / full solver logs into context; skills return summaries only. Long tasks (6 h) will blow any context window without this.
5. **Anti-loop rules from Gemma.** Never repeat an identical failed call; two failures → switch tool/approach. A 6-hour task is where a looping agent dies quietly.
6. **Cost-aware attempt budget.** Score-vs-cost is a rubric criterion AND a ranking dimension. Cap model calls per task, log tokens/calls/runtime per task, and plot the plateau — the writeup needs it anyway.
